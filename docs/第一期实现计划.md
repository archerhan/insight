# 灼见 · 第一期实现计划（种子用户可用的 Web MVP）

> 目标：让一个用户从广场进来，能完整走完"发起/围观 → 反驳/回应 → 挂红计时 → 采纳/出结论书 → 立场变更留痕 → 导出"，全链路无断点，并让 20–50 名种子用户跑通闭环、攒下第一批真实数据。
> 依赖：数据库按《数据库设计.md》v0.2 落地（含 v0.2 闭环补充表）；理由层口径已冻结（`parent_id IS NULL` = 理由层，主张型议题的致命反驳经确认自动提升）。
> 技术栈（已确认）：Next.js + TypeScript + TailwindCSS + shadcn/ui + PostgreSQL（宿主 **Neon**）。
> 质量与交付（已确认）：单元测试随功能交付、不后补；代码托管 GitHub；部署 Vercel。

## 一、第一期范围界定

### 做

- Web（Next.js 一体化）+ PostgreSQL；认证、用户档案、广场、议题三视图、发起向导。
- 论点树核心：挂载/反驳/回应/挂红计时（3/7/14 天自动流转）、击穿传播（悬空/moot）、修订与提升通道的**最小实现**（提升先由楼主+复核人操作并留 verdict）。
- 结论书：版本化 + 采纳条目 + 支撑链快照 + Markdown 导出 + 未决风险区。
- 立场变更：证词落库（stance_changes）、诚实/说服战绩记录、个人页立场时间线。
- 立帖为证**最小版**：押注记录、到期状态翻转、reality_check 落库、楼主回访（先做 T+30 提示行）。
- 激励**记录型**先行：reputation_events 计战绩；逻辑币 ledger 只建表记账，不开放可花费功能。
- 通知最小集：挂红提醒、揭晓/回访提醒（站内信形式）。

### 不做（明确推到第二期）

- 陪审团完整体系、上诉、权重制治理（陪审工作台）；
- 可花费/可兑换的逻辑币经济、悬赏支付；
- 实时 WebSocket、移动端、搜索、PDF 精排导出；
- 邀请制/好友局、徽章成就系统（只展示派生计数）；
- 反作弊体系（仅保留最基本的风控日志）。

## 二、里程碑与验收标准

### M0 数据层与树工具（约 1 周）

交付：

- Next.js + TypeScript + Tailwind + shadcn/ui 骨架；Neon 迁移脚本（v0.2 的 P0 表 + stance_changes / reputation_events 最小列 + challenges 计时字段）；
- GitHub 仓库与 CI：main + feature 分支，PR 必须通过 lint / typecheck / 单元测试 / build；
- Vercel 接入：PR 自动 preview，main 合并自动发布生产；环境变量分 preview / production；
- 数据库迁移与运行时解耦：迁移脚本进仓库，由 CI/手动命令执行，不在 Serverless 运行时里跑；
- 数据访问走 repository 层：按 Neon 落地，未来若换宿主只换 adapter；
- 测试基座：Vitest + React Testing Library 就位，树工具/状态机首批纯函数用例全绿；
- 种子数据：按新口径迁移"要不要裸辞去大理开民宿"与"AI 编程是否提高效率"两棵演示树（理由层 → 子论点 → 证据）；
- 树操作事务层：create_claim、挂反驳即建 challenge、respond、revise（supersedes）、promote/migrate（同事务重写子树 ancestors）；
- 计时 worker 骨架（3/7/14 天状态迁移 + claim_events 留痕）。Vercel Hobby 的 Cron 仅每日一次（03:00 UTC），低粒度由"读取时惰性推进"兜底，需要更高频率时再换 GitHub Actions 定时或升级 Pro。

验收：用 SQL/脚本能把一棵演示树从"反驳挂上"走到"击穿并自动提升击杀链顶端"，事件表可回放时间轴。

> 测试纪律：此后每个里程碑的交付物必须包含对应单元测试并通过 CI，才算完成；不允许"功能先行、测试后补"。

### M1 认证与全局壳（约 0.5 周）

- NextAuth（邮箱 + GitHub 其一即可），注册即建 users 档案；
- 5 分钟《理性讨论须知》占位页，完成后方可发布；
- 全局壳：灼见顶栏（广场/我的战绩/发起话题）+ 议题页内三视图切换条。

### M2 广场与发起话题（约 1 周）

- 广场：正在对线 / 最新结论书 / 即将揭晓 / 右侧战绩速览（按 _数据库设计_ 的查询模板）；
- 发起三步向导：类型（做选择/验证观点）→ 主张与背景 + 倾向 + 标签 + 首条论据 → 规则（立帖为证日期、公开范围）与发布预览；
- 发布为单事务：topic + 理由层根立场 + 可选 evidence + tags。

验收：种子用户 2 分钟内能发出一个话题，广场立即可见。

### M3 对线核心（约 1.5–2 周，最高风险）

- 对线视图：焦点下钻（面包屑 + 支持/反驳两栏 + 未决红条）读 claims/challenges；
- 发反驳流程：先写"复述对方观点"→ AI 程序检查（复述/重复/侮辱，本地启发式先行，LLM 可开关）→ 通过后建反驳节点 + challenge（target 挂红）；
- 作者侧：回应（可附反驳节点）、承认击穿（置 refuted + 自动传播悬空/moot）、修订（supersedes + 可选抢救迁移）；
- worker 到期流转 + 未决反驳在结论书降权展示的查询。

验收：两个测试账号能完成一次完整"反驳 → 对方未回应变橙/红 → 回应或承认"流程，且每步都有 claim_events。

### M4 采纳、结论书与立场变更（约 1 周）

- 楼主采纳：只允许理由层节点（或带提升 verdict 的节点），写入 conclusion_items 并附 support_chain 快照；
- 出结论书 v1：正文 + 未决风险清单（来自 open challenges）；带险关闭需逐条勾选未决反驳；
- 导出 Markdown（简要版先行）；
- 立场变更：楼主"我改主意了"向导（from → to → 证词 → 选择说服来源）→ stance_changes + honest/persuasion 记录 + 个人页时间线；
- 话题状态收敛后默认落结论书视图。

验收：一个话题能产出可导出的 v1 结论书；改主意的人能在战绩页看到带证词的时间线。

### M5 战绩、押注最小版与通知（约 0.5–1 周）

- reputation_events → user_stats 计数（判断力先做押注命中率，裁定权重先置 1）；
- 我的战绩页：立场时间线 + 我的话题 + 我的押注（记录级）+ 徽章占位；
- 押注：话题页"立帖为证"登记（数量封顶），到期 worker 翻转状态并写 reality_check；
- 回访：结论书发布后 T+30 生成 followup 提示（先站内）；
- 通知最小表 + 站内收件列表。

### M6 种子验证与迭代（2–4 周）

- 邀请 20–50 名对"理性争论/人生决策"有真实需求的种子用户（从独立开发、产品、律师/研究者圈层起步）；
- 核心指标：
  - 完整闭环完成率：发起 → ≥1 条反驳 → 作者回应 → 采纳/出结论书；
  - 3 日留存；立场变更次数/活跃用户；未决反驳回应率；
  - 单话题从发起到收敛的天数中位数；
- 每两周复盘一次，只修阻点，不提前做第二期功能。

## 三、关键实现顺序的理由

1. 先做树工具与事件层，再碰页面——状态迁移是全部功能的地基；
2. 对线（M3）放在采纳/结论书之前——没有"可回应的反驳"，结论书只是空壳；
3. 立场变更紧跟结论书（M4）——它是产品信任资产，必须在第一批真实话题中出现；
4. 押注/揭晓只做记录级最小版——机制依赖真实时间（3 个月），先让数据结构跑起来，不阻塞种子验证；
5. 陪审等治理体系整体后置——人工流程成本高，等有真实争议量再上线。

## 四、第一期默认技术口径

- Next.js App Router + Server Components（页面/查询），轻量 client 组件负责交互；
- 数据库直接用 PostgreSQL（宿主 Neon），ORM 选型 Drizzle/Prisma 在 M0 冻结；
- 计时用数据库驱动 + Vercel Cron 每日触发 + 读取时惰性推进（兜底）；更高频率需 Pro/GitHub Actions，M0 冻结此策略；
- AI 程序检查做成可开关服务：默认只做规则/启发式，LLM 校验按需启用并全部落 ai_flags；
- 权限：Neon 无内置 RLS，统一收敛在服务端 repository 层——话题/论点公开读、写限作者、vote/ledger 明细仅服务端可见。

## 五、工程质量与发布流程

### 测试策略（随功能交付）

- **单元测试（Vitest）**：覆盖树事务、状态机迁移、计时到期、裁决聚合、奖励账本、立场变更 novelty 校验等纯 TS/查询逻辑；DB 相关用例跑在可丢弃的测试库（迁移脚本建 schema）；
- **组件测试（React Testing Library）**：只测关键交互（下钻、支持/反驳切换、采纳弹窗、带险关闭勾选）；
- **AI 检查**：单测一律 mock 模型输出，只测编排逻辑；模型质量另做集成冒烟，不阻塞 CI；
- **覆盖率门槛**：核心状态机与树操作分支覆盖 ≥85%，全仓行覆盖 ≥70%（M0 起设卡）；
- **E2E（Playwright，冒烟级）**：M3/M4 收尾时补 3 条关键路径——发起 → 反驳 → 回应；采纳 → 出结论书；立场变更留痕。

### CI/CD 与数据安全

- PR 全绿（lint + typecheck + unit + build）才可合并；main 合并即触发 Vercel 生产发布；
- 数据库迁移由 CI/手动命令执行，不进 Serverless 运行时；用 Neon 分支为 preview 隔离迁移环境；
- 种子数据只在 dev/preview 可用；生产数据用受保护的管理命令写入。

### 质量红线

以下情况不允许合并：违反状态机的无依据迁移；缺 verdict 的状态变更；核心树/账本逻辑无单元测试。

## 六、风险与对策

| 风险 | 对策 |
|---|---|
| AI 程序检查误伤反驳热情 | 只标记不处罚；标记可申诉；人工复核兜底 |
| 计时 worker 漏跑导致状态卡死 | 每次读取时兜底"过期即迁移" + 每日 Cron 对账任务 |
| 冷启动无人反驳 | 种子数据 + 编辑先发高质量示例；邀请制小圈子起步 |
| 立场变更长时间为零 | 把它设为核心指标之一；楼主向导在采纳时主动提示"是否被说服" |
| 树越深越难读 | 一期先限深度 6，路径模式后置 |

## 七、第一期结束的判断标准

- 有 ≥10 个话题走到"出结论书"；
- 有 ≥3 次公开立场变更（含证词）；
- 完整闭环完成率 ≥40%（发起后 7 天内）；
- 3 日留存 ≥25%；
- 结论书导出被实际使用过（≥10 次）。

达标后再进入第二期：完整陪审治理、逻辑币可花费、移动端设计。

## 八、待定项（M0 前冻结）

### Postgres 宿主：已定为 Neon（决策记录）

决策依据：

1. 认证自己做 NextAuth → 不需要 Supabase Auth；
2. 实时订阅 / 对象存储后置 → 不需要 Supabase Realtime / Storage；
3. 无特别计费 / 运维考量 → 选架构最顺的纯 Postgres。

影响：

- 无内置 RLS：权限全部收敛在服务端 repository 层（公开读、作者写、ledger/vote 仅服务端可见）；
- 迁移用 Neon 分支做 preview 隔离，CI 执行；
- 未来若需要 Supabase 类能力，只换 adapter，不推倒重来。

### 其他待定

- ORM/查询层：Drizzle 还是 Prisma（M0 冻结）；
- 计时 worker：已冻结为"Vercel Cron 每日一次 + 读取时惰性推进"（Hobby 限制），高频化后置；
- 头像存储：先占位，一期可不提供上传。
