# 灼见 · 数据库设计（PostgreSQL · 宿主 Neon）

> 状态：设计稿 v0.2，随产品规则调整迭代。
> v0.2 变更：补齐 reputation_events / stance_changes / decision_followups / appeals；reality_checks 支持论点级终审；claims 增加 adjudicated；challenges 区分"弃战/默认判负"；verdicts 增加上诉窗口；user_stats 增加决策战绩；定死理由层口径；补充提升/迁移的祖先链一致性规则。
> 上游依据：《裁判机制设计.md》（状态机、裁判阶梯、采纳/导出规则）、《奖惩机制设计.md》（逻辑币/战绩）、《灼见产品总览与页面串联.md》（页面与旅程）及 design/ 下六份 HTML 示意稿。

## 一、设计目标与约定

1. **树是证据库，结论书是产品**：论点的"当前状态"与"历史事件"分开存储；一切状态迁移留痕（claim_events / verdicts）。
2. **裁决账本是一等公民**：凡是影响树走向、用户战绩、币余额的动作，都必须能回溯到一条裁定记录。
3. **快照优先**：结论书采纳时的支撑链、导出时的统计，都以快照落库，防止后续树变化改写历史。
4. **不做物理删除**：内容只有折叠/归档状态；仅系统性作弊（水军）在人工复核后允许硬删。
5. 主键一律 `uuid`（`gen_random_uuid()`）；时间一律 `timestamptz`；状态用 `varchar + CHECK`（方便演进，不做 PG enum）。

## 二、领域模型总览

```text
users ──1:N── topics（议题/决策问题）
                  │
                  ├─1:N─ claims（论点树：parent_id 自引用，pro/con 边）
                  │        ├─1:N─ evidence（事实论据，挂在论点下，不参与树）
                  │        ├─1:N─ challenges（反驳挂红计时：target vs challenger）
                  │        └─1:N─ claim_events（论点时间轴）
                  │
                  ├─1:N─ predictions + reality_checks（立帖为证与揭晓）
                  │
                  └─1:N─ conclusion_versions
                           └─1:N─ conclusion_items（采纳条目 + 支撑链快照）

verdicts（裁定）
  ├─1:N─ jury_sessions ── jury_members / jury_votes（陪审）
  └─影响：claims.status、challenges.status、conclusion_versions、coin_ledger、user_stats

coin_ledger + reward_rules（逻辑币流水）
user_stats + reputation_events（战绩/校准，可由账本重算）
```

### 5. claims（论点树节点）

**核心自引用树**。`parent_id = NULL` 表示直接挂在议题下的"立场/主论点"层；`relation` 表示与父论点的关系。

| 列 | 类型 | 说明 |
|---|---|---|
| id | uuid PK | |
| topic_id | uuid NOT NULL FK topics | |
| parent_id | uuid NULL FK claims | NULL = 议题直属（理由层/主论点） |
| relation | varchar CHECK IN ('root','pro','con','addon','question') | 对父论点的关系；parent 为 NULL 时为 root 立场 |
| content_title | text NOT NULL | 一句话主张（UI 常显） |
| content_body | text | 展开正文 |
| author_id | uuid NOT NULL FK users | |
| status | varchar CHECK IN ('pending','active','challenged','disputed','responded','refuted','orphaned','moot','merged','collapsed','superseded','adjudicated') | 当前状态（状态机见裁判文档） |
| depth | smallint NOT NULL DEFAULT 0 | 冗余层级（插入时由父节点+1） |
| ancestors | uuid[] NOT NULL DEFAULT '{}' | 祖先链数组，替代递归/ltree 做子查询与路径展示 |
| supersedes_claim_id | uuid NULL FK claims | 修订版本指向被取代的旧版 |
| created_at / updated_at | timestamptz | |

CHECK：`parent_id IS NULL OR relation IN ('pro','con','addon','question')`；`depth <= 12`（防失控深树，UI 路径模式限制）。

> 设计要点：
> - **采纳只限"理由层（parent_id IS NULL 且 relation 为立场）"，深层经提升通道进入**——该规则由应用层校验，并写入 verdicts；
> - "被击穿/悬空/moot"的自动传播由事件处理器完成：父被击穿 → 沿 `ancestors @> ARRAY[父id]` 批量把支撑型子孙置 orphaned、反驳型后代置 moot（详见第七节）；
> - 修订 = 新建一行并 `supersedes_claim_id` 指向旧行，旧行置 superseded，反驳链继续指向旧行。
> - 被现实终审（预测揭晓/回访验证）的论点置 `adjudicated`，关联 `reality_checks.target_claim_id` 可回溯结果。
> - **理由层口径（已定）**：`parent_id IS NULL` 即理由层；主张型议题把"待验证的主张"作为理由层根立场发布，其致命反驳被确认击穿后，击杀链顶端**自动提升**为理由层（parent 置 NULL + 写入 adoption verdict 与 promoted 事件），从而进入结论书正文——与"要不要裸辞去大理开民宿"两份演示数据的结构对齐。

## 四、关键完整性规则（CHECK 摘要）

1. `claims.parent_id IS NOT NULL` 时，`parent_id != id`，且 `topic_id` 与父一致；
2. `verdicts` 裁决对象按 kind 只允许一组目标列非空（应用层 + CHECK）；
3. `challenges.challenger_claim_id.relation = 'con'` 且与 target 同 topic、同父（应用层保证"只回应父断言"）；
4. 论据采纳：`conclusion_items.claim_id` 必须是理由层或经提升通道（提升本身有 verdict）；
5. 币流水：`balance_after = 上一笔 + delta`，定期用 `SUM(delta)` 对账 `users.coin_balance`。

## 六、核心示例查询

### 1) 某论点的直接子论点（局部邻域）

```sql
SELECT id, relation, content_title, status
FROM claims
WHERE parent_id = :claim_id AND status <> 'collapsed'
ORDER BY relation DESC, created_at;
```

### 2) 某论点的全部后代（击穿传播用）

```sql
SELECT id FROM claims
WHERE topic_id = :topic_id AND ancestors @> ARRAY[:claim_id]::uuid[];
```

### 3) 广场"正在对线"（含未决反驳计数）

```sql
SELECT t.id, t.title, t.status, t.node_count, t.open_challenge_count, t.last_activity_at
FROM topics t
WHERE t.status = 'open'
ORDER BY t.last_activity_at DESC;
```

### 4) 未决反驳清单（结论书红色风险区）

```sql
SELECT c.target_claim_id, ch.challenger_claim_id,
       ch.default_loss_at, cl.content_title AS challenge_title
FROM challenges ch
JOIN claims c ON c.id = ch.target_claim_id
JOIN claims cl ON cl.id = ch.challenger_claim_id
WHERE ch.status = 'open' AND ch.topic_id = :topic_id
ORDER BY ch.default_loss_at;
```

### 5) 导出结论书（当前版本正文 + 脚注）

```sql
SELECT ci.position, ci.role, cl.content_title, ci.support_chain
FROM conclusion_items ci
JOIN claims cl ON cl.id = ci.claim_id
WHERE ci.version_id = :current_version_id
ORDER BY ci.position;
```

## 七、状态迁移与事件（实现约定）

- 所有状态迁移**单写者**：应用服务更新 claims.status 的同时插入 claim_events，必要时写 verdicts；同事务提交。
- 计时（3/7/14 天）由定时 worker（pg_cron / 队列）扫描 challenges 执行到期动作并写 `challenge_timer` 事件。
- 父论点 refuted 的批量传播（同一事务）：
  1. 支撑型子孙（沿 ancestors）→ `orphaned`，逐条写事件；
  2. 反驳型后代 → `moot`（击杀链节点除外，其命中事实以 verdict 单独表彰）；
  3. 该父的 open challenges → `moot`。
- **提升 / 抢救迁移（重挂父节点）的一致性规则**：只允许同 topic 内迁移；父节点变更必须同事务批量重写该节点及其全部后代的 `ancestors`；旧路径写 claim_events(promoted/migrated) 并关联 verdict；目标必须是理由层（parent 置 NULL）或同层可挂载点。
- **主张被击穿后的自动提升**：根立场 refuted 且击杀链确认后，击杀链顶端节点 parent 置 NULL（理由层），写 adoption verdict + promoted 事件，随后可进入结论书。
- **改换阵营写入顺序**：novelty 校验通过 → 写 stance_changes → 同时写 claim_events(stance_changed) → 诚实奖励入 ledger → 若 source_claim 有作者，其 persuader 战绩入 reputation_events。
- 楼主"带未决风险关闭"：topic → risk_closed，创建 conclusion_version（settlement=risk_closed），并把未决 challenge 快照写入版本 payload；留待现实审计。
- 陪审裁决通过后：写 verdicts(passed) → 驱动 claims/challenges 迁移 → 奖励按 reason_code 入 ledger → 更新 user_stats。
